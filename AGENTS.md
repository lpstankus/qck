# Repository Guidelines

## Project Structure & Module Organization

This is a Lua Neovim plugin. Runtime source lives under `lua/qck`.

- `lua/qck/init.lua` exposes the public `require("qck")` API.
- `lua/qck/app/` wires plugin setup and terminal integration, including task and agent terminal reuse.
- `lua/qck/ui/` owns tab state, layout, shared form creation, rendering, and runtime UI behavior.
- `lua/qck/ui/form.lua` owns shared text and selection field behavior for floating forms.
- `lua/qck/tasks/` handles task form submission behavior, persistence, and task execution.
- `lua/qck/agents/` handles global agent command configuration and local CWD overrides.
- `lua/qck/shared/` contains small reusable helpers for commands, keymaps, notifications, autocmds, and shared type annotations.
- `tests/` contains the headless Neovim test harness, smoke scenarios, helpers, and vendored `mini.nvim`/LuaCov code.

## Build, Test, and Development Commands

There is no package manager wrapper in this repository. Use Neovim directly:

```sh
nvim --headless --clean -u NONE -l tests/minitest.lua
```

Runs the MiniTest smoke suite in an isolated XDG test environment.

```sh
nvim --headless --clean -u NONE -l tests/coverage.lua
nvim --headless --clean -u NONE -l tests/luacov_report.lua
```

Runs coverage scenarios and generates the LuaCov report using `tests/.coverage`.

## Coding Style & Naming Conventions

Use idiomatic Lua with two-space indentation, local modules, and explicit `require("qck...")` dependencies near the top of each file. Public APIs use simple function names such as `open`, `close`, `run_task`, and `set_agent`. Keep type comments in LuaLS style (`---@param`, `---@return`, `---@class`) when adding or changing module contracts.

Prefer small module-level helper functions over object-like APIs. Keep user-facing labels, category keys, and persisted storage names stable unless the change is intentional and covered by tests.

## Testing Guidelines

Add behavior coverage in `tests/scenarios.lua` and expose it through `tests/test_smoke.lua` when changing plugin behavior. Use helpers from `tests/helpers.lua` instead of touching real user config or state. Test runs must remain hermetic through `tests/bootstrap.lua` XDG setup.

Name scenarios after observable behavior, not implementation details.

## Commit & Pull Request Guidelines

- Commit messages should be short, imperative, and scoped (example: `add multi terminal management api`).
- Keep one logical change per commit.
- After committing any code chunk, update `AGENTS.md` to reflect the new current architecture/guidelines.
- For any commit that includes AI-generated code, the commit body must include exactly: `Commit generated by AI`.

Pull requests should describe the behavior change, list the test command run, and include screenshots or terminal captures when UI behavior changes.
